## 結論

全機能を通してレビューし、**クリティカル1件・高2件・中12件・低11件**を検出、すべて修正しました。
巡回レビューは7巡で終了しています（8巡目に入る条件を満たさなかったため。理由は[巡回レビューの経過](#巡回レビューの経過)）。

今回いちばん重かったのは、**ランキング画面が終日運転で落ちる**経路（クリティカル）です。
表示したカード画像（1枚あたり文字列で約7MB）を解放せずに抱え続けており、3000人規模では数十GBに達します。
会場の大画面が消えても記録自体は残るため、**気づくのが「画面が固まってから」になる**のが最も危ないところでした。

そのほか、この製品の性格（当日やり直しがきかない・成果物を後日公開する）から、
**「静かに劣化して誰も気づかない」経路**を重点的に潰しています。

## 指摘と対応の一覧

### クリティカル

#### C-1. ランキング画面が抱えるカード画像を解放せず、終日運転でメモリを使い切る

- **場所**: `src/renderer/components/ranking/PaginatedScrollList.tsx`
- **症状**: 一度表示した回のカード画像（data URL）を無制限に保持。
  1枚 2.5MB の PNG が base64 で約3.4MB、JS の文字列（UTF-16）としては約7MB。
  「みんなのきろく」は新しい30件しか見せないが、当日は3000人が遊ぶため、
  一日で数十GBに達して**ランキング画面（会場の大画面）が落ちる**。
- **併発**: 同じ effect が `imageUrls`（state）に依存していたため、
  カードが未生成の回（＝main が null を返す回）について
  **IPC とディスク読み取りが無限ループ**していた。「じゅんび中」が1枚でもあれば発生する。
- **対応**: 取得済み判定を ref に移して依存から外し（無限ループの解消）、
  一覧から外れた回の data URL は明示的に解放。未生成の回は5秒間隔で取り直す。
- **確認**: 通しテストでランキング画面のカード表示4枚・No Image 0件。

### 高

#### H-1. 救済スクリプトが保守ロックを取らず、稼働中のアプリと競合し得た

- **場所**: `src/test/memorial-card-recovery.ts`（`npm run recovery`）
- **症状**: `tools/retry-failed.cjs` は保守ロック（`.maintenance.lock`）を取るのに、
  `npm run recovery` は取っていなかった。アプリを起動したまま走らせる運用があるため、
  **アプリの起動時点検が「壊れている」と判断した直後にこちらが正常なカードを完成させ、
  点検側がその新しいカードを退避する**——という取り返しのつかない競合が成立する。
- **対応**: ロックの取得と解放（Ctrl-C 含む）を追加。
  ただし `retry-failed --apply` は自分がロックを取ってから recovery を呼ぶため、
  そこから来た場合は取り直さない（`KIDSPG_MAINTENANCE_LOCK_HELD=1` で伝える）。
  取りに行くと**親のロックで自分が弾かれ、1件も直せなくなる**ため。
- **確認**: 回帰テスト3件を追加（`tools/test-retry-failed.cjs`）。

#### H-2. 救済ツールの ComfyUI 問い合わせに時間上限がなく、ぶら下がる

- **場所**: `tools/retry-failed.cjs`
- **症状**: `/upload/image` `/prompt` `/history` `/view` `/system_stats` のすべてに
  タイムアウトが無い。ComfyUI が TCP レベルで無応答（メモリ不足でスワップ中など）だと
  `fetch` が返らず、`while (Date.now() < deadline)` の判定にすら到達しない。
  `--timeout-min` を指定しても効かず、**保守ロックを握ったままぶら下がるので
  アプリの起動時点検まで止まる**。`comfyui-worker.ts` は同じ理由で上限を付けてある。
- **対応**: すべての問い合わせに上限を付け、進捗確認の失敗は打ち切り判定へ戻す。

### 中

#### M-1. 起動時点検のカーソルが、間の未点検の回を飛び越える

- **場所**: `src/main/services/startup-consistency.ts`
- **症状**: 「前回どこまで見たか」のカーソルを、**表示キャッシュが参照している回まで含めて**
  算出していた。`ranking_top` はスコア順で時刻と無相関（朝イチの高得点は終日1位に居座る）。
  この古い1件を点検しただけでカーソルがそこまで飛び、
  **間に挟まった数百件が何度再起動しても永久に点検されない**。
  カードの実体はあるのに正本（`result.json`）がプレースホルダを指したままになり、
  その子が後日の公開物から欠ける。
- **対応**: カーソルは「順番に回している分」からのみ進める。
  続きを1件も消化できなかった起動ではカーソルを動かさない。
- **確認**: 回帰テストを追加。**修正を元に戻すとテストが落ちる**ことまで確認済み。

#### M-2. ランキング設定が固定され、保存・再読み込みが反映されない

- **場所**: `src/main/services/ranking-service.ts`
- **症状**: `getRankingConfig()` が一度読んだ config を保持し続けるため、
  設定画面でページ送りの間隔やタイル寸法を変えても**ランキング画面だけ古い値で動き続ける**。
  画面には何も出ないので、当日は「効かない」としか分からない。
- **対応**: 毎回読み直す（呼ばれるのはランキング画面を開いたときだけで費用はない）。
  読めなかったときに限り直前の内容を返す。

#### M-3. ウィンドウが無い状態で終了確認に入るとアプリを終了できない

- **場所**: `src/main/main.ts`
- **症状**: `before-quit` / `close` は `exitConfirmed` が立つまで preventDefault し続けるが、
  確認を出す相手（mainWindow）が無いと `showExitConfirmation` は黙って戻る。
  結果、**× もタスクバーからの終了も効かない**状態になる。レンダラーが落ちたときに実際に起こる。
- **対応**: 相手が居ない場合はそのまま終了させる（確認すべきものも無いため）。

#### M-4. ComfyUI 応答待ちのリスナーがタイムアウト時に解除されず積み上がる

- **場所**: `src/main/services/comfyui-service.ts`
- **症状**: `waitForReady` / `preUploadImage` / `getStatus` / `healthCheck` のいずれも、
  解除がハンドラ側にしか無かった。プリアップロードは1プレイに1回走るため、
  ComfyUI が重い日には待ち受けが積み上がり `MaxListenersExceededWarning`（既定10件）に達する。
- **対応**: 待ち受けの管理を `waitForWorkerMessage` の1か所に集約し、解除漏れが起きない形にした。

#### M-5. ComfyUI ワーカーが死んでも参照を持ち続け、以後の投入が黙って消える

- **場所**: `src/main/services/comfyui-service.ts`
- **症状**: ワーカーは `uncaughtException` で `process.exit(1)` する。
  参照を持ったままだと以後の `postMessage` は例外も出さずに捨てられ、
  **「撮影は通るのに AI 画像だけが一枚も来ない」**という無言の劣化になる。
- **対応**: `exit` で参照を捨て、レンダラーへも知らせる。
  終了処理中（`destroy()`）は区別して嘘のエラーを出さない。

#### M-6. 撮影で真っ黒な写真が保存され得る

- **場所**: `src/renderer/pages/CameraPage.tsx`
- **症状**: `srcObject` を差してから最初のフレームが届くまで `videoWidth` は 0。
  その状態で撮ると 0×0 のキャンバスから**真っ黒な写真**が出来て保存され、
  そのまま AI 変換にも回る。本人には気づけない。
- **対応**: 映像が来ていなければ撮影せず、待つよう案内する。

#### M-7. カメラの初期化が設定より先に走り、ダミー写真の寸法がずれる

- **場所**: `src/renderer/contexts/CameraContext.tsx`
- **症状**: カメラが無い場合のダミー写真は `camera.width` で作られるが、
  初期化が config より先に走るため既定値（380px）で焼かれ、
  config.json の撮影解像度（300px）と食い違ったサイズの画像が後段へ流れていた。
- **対応**: 設定の読み込みを待ってから初期化する。

#### M-8. 生成パラメータの点検結果（`denoise: 1` など）が画面に出ない

- **場所**: `src/main/preload.ts` / `ConfigContext.tsx` / `TestPage.tsx`
- **症状**: main は保存・再読み込みのたびにワークフローの配線を点検して
  `warnings` を返しているのに、**preload の型から漏れていて**画面まで届いていなかった。
  `denoise: 1` のように「範囲内なので保存はできるが、絵が写真とほぼ無関係になる」設定は、
  起動時ダイアログを過ぎたあとはここでしか気づけない。
- **対応**: 型を通し、保存時・再読み込み時の両方で表示する。

#### M-9. 終了確認ダイアログの「処理中」件数が常に 0

- **場所**: `src/main/main.ts`
- **症状**: `serverQueueRunning` / `serverQueuePending` を常に 0 で返していたため、
  実際に1枚生成している最中でも「処理中: 0件 / 待機中: 1件」と出ていた。
  閉店時にスタッフが「いま止めても大丈夫か」を判断する唯一の材料。
- **対応**: 手元が知っているジョブの状態から実数を出す
  （ComfyUI へ聞きに行くと最大5秒ダイアログが出ず、× が無反応に見えるため採らない）。
  2か所に重複していた組み立ても集約。

#### M-10. 公開物を集める `collect-cards` が壊れたカードを混ぜていた

- **場所**: `src/test/collect-cards.ts`
- **症状**: ファイル名だけでカードを選んでおり、書き込み途中で切れた PNG を
  そのまま `card_images/` へコピーしていた。**後日公開の最後の関門**でこれをやると、
  半分だけのカードが公開物として確定する。
- **対応**: 完全性を検査し、壊れた回は集めずに作り直しの案内を出す。
  「検査できなかっただけ」（OneDrive のロック等）は集める側に倒す。
- **確認**: 壊れたカードを含む一時ディレクトリで除外されることを確認。

#### M-11. ギャラリー一覧が壊れたカード・古い AI 画像を載せる

- **場所**: `src/test/create-image-path-json.ts`
- **症状**: (a) カードを名前だけで選んでおり、切れた PNG を一覧に載せていた
  （2026-09-02 の「上半分だけ表示」の再現経路）。
  (b) `anime_photo` が readdir 順の先頭1件を採っており、切れた `_00001_` が残っている回で
  古い方を載せていた。
- **対応**: 完全性を確かめ、新しい順に完全なものを選ぶ
  （`findAnimePhotoPath` / `retry-failed` と同じ扱いへ統一）。

#### M-12. `results.json` の型が別名で二重定義され、実体と食い違う型が置かれていた

- **場所**: `src/shared/types/ranking.ts`
- **症状**: 書き手（main）は `results.ts` の型、読み手（レンダラ）は `ranking.ts` の型と、
  同じファイルの形が2か所で定義されていた。片方に項目を足すともう片方が黙って食い違う。
  さらに「仕様に定義が無いので推測で置いた」という注記つきの `GameResult` があり、
  実際の `result.json` と食い違っていた（`timestampJST` ではなく `timestamp`、`rank` なし）。
  誤って import すると**型は通るのに中身が合わない**という追いにくい不具合になる。
- **対応**: `results.ts` へ一本化して再輸出し、誤った `GameResult` を削除。

## リファクタリング

「定数や関数はあるが誰も見ていない」状態は、**当日そこを直せば効くという誤解**を生みます。
この製品ではそれが直接、記念カードの取りこぼしにつながるため、参照の無いものは削除しました。

**削除したデッドコード**

- `MemorialCardService`: `generateFromDummyImage` / `handleComfyUICompletion` / `getConfig` / `getStatus`
- `ElectronApp.ensureDirectoryExists`（`process.cwd()` 基準。`paths.ts` が戒めている書き方そのもの）
- `helpers`: `generateSafeFileName` / `sanitizeNickname`
- `assets.ts`: `loadAssets` / `getImage` / `preloadPixiAssets` / `isPixiAssetsPreloaded`
  （`getAssetManager` と `AssetManager` は非公開化。成功時の大量ログも削除）
- `constants.ts`: `GAME_CONFIG` / `GAME_CANVAS` / `FILE_PATHS` / `SPRITE_CONFIG` / `UI_CONFIG` / `PIXI_ASSETS`、
  `TIMING_CONFIG`・`PERFORMANCE_CONFIG` の昨年の名残
- `comfyui-worker`: `loadWorkflowTemplate` と `workflowTemplate`
  （作業フォルダ基準でテンプレートを探す誤った実装。ワーカーはテンプレートを読まない）
- `ResultsManager.formatTimestamp`（恒等関数。整形していると読めるが何もしていない）
- `ImageCompositionConfig.getFontSettings`
- `TopPage` の空 effect と大きなコメントアウト

**重複の統合**

- ダミー版とAI版で同じ手順を2か所に書いていた合成処理 → `MemorialCardService.composeCard` に集約
- 同内容だった2つの合成設定生成 → `buildCompositionConfig` に集約
- rename の待ち時間表が3か所 → `card-output.renameWithRetry` に統一
- `results.json` の型が2か所 → `results.ts` に統一
- 終了確認の状態組み立てが2か所 → `collectExitStatus` に集約

**出どころの一本化**

- ウィンドウサイズ: `main.ts` が幅 1200 を、ランキング側が高さ 768 を直書きしており、
  `WINDOW_CONFIG` を直しても片方しか変わらなかった → 定数へ寄せ、`ranking` を追加
- `image-composition-config` のメソッド内 `require('fs')` → 先頭 import へ

## 対応しなかった指摘（判断と理由）

いずれも動作に影響しないと判断したものです。

1. **`ShinyWaveBackground` の時刻精度**
   シェーダへ渡す経過秒は float32 で、12時間連続稼働すると量子化幅が
   1フレームの位相変化の 1/4 程度になり、わずかな揺らぎが出得る。
   ただし打ち消すには一定時間ごとに位相を飛ばす必要があり、
   **1時間ごとに背景が跳ねる方が体感として悪い**。1日で再起動する運用なので現状維持。

2. **`TopList` / `RecentList` / `ScrollableCardList` が素通しのラッパー**
   3層とも props をそのまま渡すだけで、実体は `PaginatedScrollList`。
   統合できるが、当日を控えて表示側の構造を触る利得が小さいため見送り。

3. **`comfyui-worker` の `electronFetch` が https に非対応**
   `http.request` のみを使っている。現行 config の2プロファイルはどちらも http なので影響なし。
   AIサーバーを https 化する場合はここの対応が必要。
