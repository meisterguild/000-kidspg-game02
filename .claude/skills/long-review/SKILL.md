# 長時間離席時のレビュー＆修正ループ

## これは何のためか

利用者が席を外しているあいだ、**品質を上げることだけ**を目的に自走する。

🔴 **新しい機能を足す時間ではない。** 離席中に仕様を増やすと、戻ってきた利用者が
「何が変わったのか」を把握できないまま当日を迎えることになる。やるのは
**すでにあるものの欠陥を見つけて直すこと**に限る。

## 1巡の流れ

```
① レビュー（サブエージェント・敵対的）
      ↓ 指摘あり
② 修正（自分で直す）
      ↓
③ 再レビュー（同じ観点で、直ったかを確かめる）
      ↓ 指摘ゼロ
④ npm run check（build / tsc / lint / test）
      ↓ 通った
⑤ commit & push
      ↓
⑥ 次の巡へ（観点を変える）
```

### ① レビューはサブエージェントに、敵対的にやらせる

**自分でレビューしない。** 自分が書いたコードを自分で見ると、書いたときの意図が
見えてしまって「そう書いたのだから正しい」と読んでしまう。

`Agent` ツールで独立したレビューアを立て、**敵対的に**（欠陥を見つける前提で）
読ませる。プロンプトには次を必ず入れる。

- **対象を絞る**（直近のコミット範囲・特定のファイル群）。「全部見て」は薄くなる
- **観点を1つに絞る**。1巡で全部見せると、どれも浅くなる
- **「問題が無い」で終わらせない**。必ず「いちばん危ういのはどこか」を答えさせる
- **実際の壊れ方を書かせる**（入力→症状）。指摘が具体的でないと直せない
- 当日の運用（オフライン・スタッフはCLIを叩けない・やり直せない）を前提として渡す

観点は巡ごとに変える。例:

| 巡 | 観点 |
|---|---|
| 1 | 直近の変更の**壊れ方**（境界値・エラー経路・失敗したときに何が残るか） |
| 2 | **当日いちばん困る失敗**（カードが出ない・写真が漏れる・起動しない）に繋がる穴 |
| 3 | バッチ・PowerShell の作法（改行・BOM・`else if`・引用符・名前一致の除外指定） |
| 4 | ドキュメントとコードの食い違い（手順書に書いた操作が本当に通るか） |
| 5 | テストが**本当に何かを守っているか**（通るだけのテスト・自分の文面を見ているだけのテスト） |

### ② 修正は自分でやる

サブエージェントに直させない（並行して同じファイルを触ると壊れる）。
指摘を受けたら、**まず再現を確かめてから**直す。再現しないものは
「再現しなかった」と記録して直さない。

### ③ 再レビューで指摘ゼロにする

CLAUDE.md の取り決め（コードレビューを必ず実施し、修正したら再レビューして
指摘をゼロにする）に従う。**直したつもりを直ったことにしない。**

### ④ テスト

`npm run check`（build / tsc / lint / test）。**1件でも落ちたら次へ進まない。**

### ⑤ commit & push

- 1巡＝1コミット（何を直したかが後から追える単位にする）
- コミットメッセージには**なぜ直したか**と**どう壊れていたか**を書く
- `main` へ push する（このリポジトリの流儀）

## いつやめるか

- **コンテキスト使用量が 80% に達したら**、その巡を締めて（テスト・commit・push まで）
  終わる。中途半端な修正を残さない
- 観点を出し尽くしたら終わる。**指摘を作るために粗探しを続けない**
- 行き詰まったら（判断が要る・実機が要る・利用者の許可が要る）**止めて通知し、待つ**

## やってはいけないこと

| | |
|---|---|
| 🔴 ファイルやデータの削除 | CLAUDE.md の方針どおり。**自分が作った検証用の一時ファイルだけ**が例外 |
| 🔴 force push・履歴の書き換え | しない |
| 🔴 仕様変更・新機能 | しない。見つけても「見つけた」と記録して報告に回す |
| 🔴 未検証の断定 | 「直したはず」を「直した」と書かない。確かめた事実だけを書く |
| 🔴 大きなリファクタリング | 当日を控えているあいだは、表示側の構造を触る利得が小さい |
| ⚠️ 実機・別PCが要る検証 | できないものは**できないと明記**して報告に回す |
| ⚠️ 長時間かかる処理の最中にソースを触る | 配布パッケージの作成中などは、コピーの整合が崩れる。終わるまで待つ |

## ntfy 通知（要所だけ）

送り方はユーザーグローバルの CLAUDE.md（terms-extra 経由）に従う。
**1分あたりの上限があるので、進捗を1行ずつ送らない。**

| いつ | 内容 |
|---|---|
| 開始 | 何巡する予定か・対象範囲 |
| 各巡の終わり | 見つけた件数と、直した内容の要点（1〜2行） |
| 行き詰まったとき | 何で止まっているか・何を判断してほしいか |
| 終了 | 何巡して何件直したか・テストの件数・push したか |

送れなくても作業は止めない（投げっぱなしで、届いたかは分からない）。

## 最後の報告に必ず入れること

- **何巡して、何を直したか**（1行ずつ）
- **再現しなかった指摘**（直していないもの）とその理由
- **できなかった検証**（実機・別PCが要るもの）
- テストの件数と結果
- push したコミット
